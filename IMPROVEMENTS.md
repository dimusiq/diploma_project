# Идеи по улучшению проекта Nebardak

Сводка того, что можно добавить, чтобы усилить функционал склада (поступления → склад → отгрузка) и общее качество приложения.

---

## 1. Домен и модели данных

### 1.1 Расширение модели Item

Сейчас: `title`, `description`, `status`, `owner_id`.

Имеет смысл добавить (по необходимости):

| Поле            | Тип     | Назначение                          |
|-----------------|---------|-------------------------------------|
| `quantity`      | int     | Количество (сейчас по сути 1 единица на запись) |
| `sku`           | str     | Артикул для поиска и отчётов        |
| `barcode`       | str     | Штрихкод для приёма/отгрузки        |
| `unit`          | str     | Единица измерения (шт, кг, л, упак.) |
| `category_id`   | FK      | Связь со справочником категорий     |
| `expires_at`    | date    | Срок годности (опционально)          |
| `location`      | str     | Ячейка/зона склада                  |
| `created_at`    | datetime| Дата поступления (для отчётов)     |

Это потребует миграций Alembic и обновления API/форм.

### 1.2 Справочник категорий

- Модель `Category` (название, родитель для иерархии).
- В `Item` — `category_id` (nullable).
- В API: CRUD категорий, в формах — выбор категории при создании/редактировании.

### 1.3 История изменений (audit log)

- Отдельная таблица `ItemHistory` или общий `AuditLog`: кто, когда, какое поле, старое/новое значение.
- Особенно полезно для `status` и `quantity`: кто и когда переместил «на склад» или «в отгрузку».
- API: `GET /items/{id}/history` (и опционально общий лог для админов).

## 2. Бизнес-логика и API

### 2.1 Валидация переходов по статусам

Сейчас в `ItemActionsMenu` можно перевести в любой из `incoming` / `warehouse` / `shipment`.

Логичнее ограничить:

- `incoming` → `warehouse` (принято на склад)
- `warehouse` → `shipment` (подготовлено к отгрузке)
- `shipment` → «отгружено» (новый статус `shipped` или архив) — опционально

Реализация: на бэкенде в `update_item` проверять допустимый переход; на фронте в меню показывать только разрешённые варианты.

### 2.2 Поиск и фильтрация

В `read_items` уже есть `status`. Имеет смысл добавить:

- `search` — поиск по `title`, `description`, `sku`, `barcode` (ILIKE или full-text).
- `owner_id` — для админов.
- `category_id`, `created_at_from`, `created_at_to` — при появлении полей.

На фронте — форма фильтров над таблицами (items, warehouse, shipment).

### 2.3 Экспорт (Excel/CSV)

- Endpoint `GET /api/v1/items/export?format=csv| xlsx&status=...&search=...`.
- На фронте — кнопка «Выгрузить» на страницах списков и, при необходимости, на дашборде.

### 2.4 Пагинация в API

Уже есть `skip`/`limit`. Можно добавить cursor-based пагинацию для больших объёмов или оставить offset — в зависимости от масштаба.

## 3. Frontend

### 3.1 Пагинация на «Склад» и «Отгрузка»

Сейчас в `warehouse.tsx` и `shipment.tsx` используется `page = 1` без `onPageChange` и без `search`.

Сделать по аналогии с `items.tsx`:

- `validateSearch` с `page`;
- `PaginationRoot` с `onPageChange` и `setPage` через `navigate({ search: { page } })`;
- `getItemsQueryOptions({ page })` с корректным `skip`.

### 3.2 Поиск и фильтры в UI

- Поле поиска (и при наличии — фильтр по категории, дате) над таблицами.
- Передавать `search`, `status` (уже есть на warehouse/shipment), `category_id` и т.п. в `readItems`.

### 3.3 Отображение ID

- Вместо полного UUID — короткий вариант, например последние 8 символов, с `Tooltip` или `title` с полным ID по ховеру.
- Упростит чтение таблиц и переписку.

### 3.4 Подтверждение при смене статуса

Перед `move.mutate(status)` показывать диалог:

- «Переместить «{title}» на склад?» с «Отмена» / «Переместить».
- Аналогично для «В отгрузку» и т.д.

### 3.5 Кнопка «Добавить» на «Склад» и «Отгрузка»

Сейчас `AddItem` только на «Поступления».

Варианты:

- Оставить добавление только в поступления (логично по потоку).
- Или на «Склад»/«Отгрузка» — вызов того же `AddItem` с подсказкой, что по умолчанию статус будет `warehouse`/`shipment` (если решите разрешить создание не из incoming).

### 3.6 Улучшение главной страницы

Сейчас приветствие и «Добро пожаловать».

Можно добавить:

- Блок «Последние поступления» (например, 5 последних items с `status=incoming` или по `created_at`).
- Блок «В отгрузке» (количество или список).
- Краткие ссылки на «Поступления», «Склад», «Отгрузка».

## 4. Дашборд

### 4.1 Графики по времени

- Поступления и отгрузки по дням/неделям за выбранный период.
- Новый endpoint, например `GET /api/v1/dashboard/trends?from=&to=&group_by=day|week`.

### 4.2 Уточнение карточек

В `dashboard.tsx` две карточки по `warehouse`:

- «В процессе» и «На складе» оба считают `status_distribution.warehouse`.

Имеет смысл разделить:

- «В процессе» — например `incoming`;
- «На складе» — `warehouse`;
- «В отгрузке» — `shipment`.

И при желании — «Отгружено» (при введении статуса `shipped`).

## 5. Безопасность и роли

### 5.1 Роли (если нужно разграничение)

Сейчас по сути: пользователь и `is_superuser`.

При росте числа пользователей:

- Роли: `admin`, `manager`, `warehouse`, `viewer` и т.п.
- Права: кто может менять статус, кто — только просмотр; кто видит чужие items.

Реализация: таблица `Role`, связь `User.role_id`, проверки в `deps` и в API.

### 5.2 Rate limiting

- Ограничение частоты запросов к `/login`, `/items`, `/users` (по IP или по `user_id` после логина).
- Например, `slowapi` или middleware на FastAPI.

## 6. Инфраструктура и качество

### 6.1 Бэкапы БД

- Скрипт (cron) `pg_dump` в object storage или на отдельный диск.
- В `DOCKER.md` или `deployment.md` — раздел «Бэкапы».

### 6.2 Логи и мониторинг

- Структурированные логи (JSON) с `request_id`, `user_id`, `path`, `status_code`.
- Опционально: Prometheus-метрики (latency, ошибки, число запросов).
- Health-check уже есть: `GET /api/v1/utils/health-check/`.

### 6.3 E2E-тесты

Расширить Playwright:

- Сценарий: логин → создание item → переход «на склад» → «в отгрузку».
- Проверка дашборда (наличие блоков, не падение).
- Сброс пароля (довести TODO в `reset-password.spec.ts`).

## 7. Дополнительные фичи

### 7.1 Печать

- Генерация PDF накладной/этикетки для отгрузки (например, по выбранным `shipment` items).
- При появлении `barcode` — печать этикеток со штрихкодом (на бэке — генерация, на фронте — кнопка «Печать»).

### 7.2 Уведомления

- При критичных действиях (например, массовая отгрузка) — отправка email на `FIRST_SUPERUSER` или на ответственных.
- Расширение существующей email-инфраструктуры.

### 7.3 PWA и офлайн

- Service Worker, `manifest.json` для установки как PWA.
- Кеширование справочников (категории, свои items) для работы при нестабильной сети — после стабилизации базового функционала.
